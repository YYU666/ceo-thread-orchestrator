# CEO Flow 中文介绍

CEO Flow 是一个给 Codex 用的开源插件。它的目标不是让 Codex 只像一个“接任务干活的人”，而是让 Codex 像一个小团队里的 CEO、产品经理和架构师一样管理项目。为了兼容已有安装和发布记录，包名仍然保留为 `ceo-thread-orchestrator`，但公开短名使用 CEO Flow。

它会把当前 Codex 线程当成最高推理的决策线程，也就是 CEO 线程。CEO 线程负责理解全局、拆任务、安排专家线程、传递记忆、检查证据，并决定工作是否可以接受。如果这个 CEO 线程已经产出了 PRD 或任务图，用户接着要求开始执行时，它应该进入轻量 Core Team 执行波次，而不是继续停在 CEO-only 规划。

## 为什么需要它

Codex 现在越来越像一个可以协作的工作空间。它可能有多个线程、worktree、自动化、subagent、本地文件、知识库和项目记忆。

能力变强之后，新的问题也出现了：

- 到底哪个线程应该做这个任务？
- 什么时候应该复用已有线程？
- 什么时候才应该新建线程？
- 线程之间怎么传递上下文？
- 新线程怎么知道项目记忆？
- 员工线程说“完成了”，CEO 要不要相信？
- 做完之后，经验应该写回哪里？

CEO Flow 就是为了解决这些协调问题。

## 核心设计

它采用“一个 CEO 大脑 + 多个专家线程”的结构。

CEO 线程负责：

- 判断项目方向和优先级
- 做架构和产品取舍
- 把用户需求拆成任务卡
- 决定是否需要新线程
- 复用已有专家线程
- 给新线程准备记忆包
- 维护轻量团队登记
- 记录有证据的经验卡
- 在线程之间转发关键信息
- 检查 worker 报告、diff、测试、截图等证据
- 做最终裁决：接受、返工、阻塞或废弃

专家线程负责具体工作：

- 普通代码实现
- 独立 review 和 QA
- UI/UX 建议
- 市场和竞品研究
- 知识库、记忆库和文档整理

简单说，CEO 不应该长期自己写所有代码。CEO 应该做“大脑”和“验收门”，把执行工作交给合适的专家。

## 默认 Core Team

CEO Flow 有一套默认公司式角色图：

- CEO / PM / Architect
- Implementation Expert
- Review / QA Expert
- Product / UX Expert
- Knowledge / Memory Expert
- Research / Docs Expert

这不是固定组织架构，也不是自动工作流引擎。角色只有在任务图需要、当前 Codex 工具允许、并且用户或项目授权执行时，才会变成真实可见专家线程。

默认 PRD 路径是：产出 PRD 的线程就是 CEO 线程；PRD 或任务图被接受后，用户说开始执行，CEO 就把工作映射到最小可用 Core Team。多数项目先用 `CEO + Implementation`；高风险或用户可见任务再加 `Review/QA`；只有确实需要产品体验、知识沉淀或外部资料时，才启用 `Product/UX`、`Knowledge/Memory` 或 `Research/Docs`。

任务派出去之后，CEO 还要负责“收菜”。它要定时读取 worker 报告，检查证据，把每条 lane 标成接受、返工、阻塞、废弃、仍在运行或已过期，然后继续发下一个未阻塞任务。worker 线程遇到范围内的日常选择，应该问 CEO，而不是问用户。只有改变已接受 PRD、超出写入范围或预算、需要凭证、涉及破坏性操作，或改变产品方向时，才需要回到用户。

## 动态分线程

这个插件不会看到任务就乱开线程。它把新建线程看成一种成本决策。

普通代码任务默认只使用一个代码线程。这个代码线程会持续做类似的代码任务，积累上下文。

只有满足这些条件时，才建议新增第二个代码线程：

- 新任务真的可以并行
- 两个任务修改的文件范围不重叠
- 两个任务可以分别验证
- 节省的时间值得额外的合并、审查和沟通成本

如果用户中途加需求，CEO 不会简单地“再开一个线程”。它会先重新看整个任务图，再决定：

- 继续交给原线程
- 排队给原代码线程
- 增加一个 review 线程
- 新建独立专家线程
- 或者废弃旧方向，重新安排

## 代码质量护栏

这个插件会把 AI 写出的代码当成“速度很快但还没验收的半成品”。派发实现任务前，CEO 要先定义架构不变量、参考文档、回滚基线、明确的文件范围和验证证据。

worker 应该避免技术栈漂移、重复逻辑、强耦合、魔法数字、随意命名、缺少边界检查，以及大范围猜测式重写。如果连续修复让代码越来越乱，CEO 应该停止循环，保留有用发现，然后选择回滚方案、新的窄任务卡，或独立只读 review。

## 目标闭环

这个插件不应该停在“我建议分几个线程”。

如果一个目标需要多步完成，CEO 线程会维护一个轻量目标简报：

- 用户真正想要的结果
- 完成标准
- 不做什么
- 任务图
- 当前活跃线程和负责人
- 最近证据
- 下一步动作
- 结束状态：接受、阻塞或废弃

每一轮 CEO 都应该推动目标往前走：派发任务、收取 worker 结果、检查证据、要求返工、接受结果、标记阻塞、废弃旧方向，或者把稳定经验写回记忆。

## 记忆和知识库

这个插件把记忆当成项目基础设施，而不是依赖聊天记录。

默认记忆顺序是：

1. 项目说明和本地记忆文件
2. 推荐的 Zhixia / `.codex-knowledge/` 知识库
3. 当前活跃线程的报告和交接信息
4. 决策日志、bug 记忆、handoff 记录和生成文档

新建线程或复用旧线程时，CEO 会准备一个精简记忆包。新线程不应该靠猜，也不应该假装自己知道其他线程的上下文。

如果项目有其他本地知识库路径，也可以由项目指定。Zhixia 是 CEO Flow 推荐的官方知识库方案，但不是每个环境都必须具备的硬依赖。

## 轻量团队登记

CEO Flow 可以为可复用专家线程保留一份小 roster：角色、能力、写入策略、信任等级、当前状态和最近证据。它也可以把可复用经验先写成证据记忆卡，记录 lesson、适用范围、不适用范围、证据、测试、置信度和状态。

这些记录只服务于 CEO 判断，不会自动启动后台 worker、自动队列、自动扩容或自修复系统。

## 安全边界

这个插件比较谨慎。

- 不假设所有 Codex 环境都有线程工具
- 不在工具要求明确授权时偷偷创建新线程
- 不把排队任务当成正在运行
- 不因为网上有某个记忆工具就强行切换记忆系统
- 不让多个 worker 同时改同一个文件范围
- 不把高成本模型浪费用在普通重复任务上
- 不把员工线程报告当成最终事实

CEO 必须看证据。worker 的报告只是证据之一，不是结论本身。

## 适合谁

它适合：

- 用 Codex 做大型项目的个人开发者
- 不懂编程但希望 Codex 像项目经理一样帮忙的人
- 需要多个 Codex 线程协作的团队
- 想把项目记忆、bug 记忆和文档沉淀下来的人
- 正在实验 AI agent 团队协作的人

## 它不是什么

它不是万能自动员工系统。

它也不能保证每个 Codex 环境都能创建线程、fork 线程或管理 worktree。它会优先遵守当前 Codex 工具的真实能力和授权要求。

如果某个环境没有线程工具，它仍然可以帮助 Codex 做规划、拆任务、写记忆包、定义验收标准和维护项目知识。

## 一个典型流程

1. 用户提出一个产品反馈或 bug。
2. CEO 线程把它整理成目标简报或任务卡。
3. CEO 定义完成标准和任务图。
4. CEO 查找有没有可复用的专家线程。
5. 普通实现交给一个代码线程。
6. 高风险变化交给独立 review 线程检查。
7. CEO 看 diff、测试、截图、报告等证据。
8. CEO 决定接受、返工、阻塞或废弃。
9. 稳定经验写回项目记忆、bug 记忆、决策日志或文档。

## 当前状态

这是一个实验性的社区插件。它会随着 Codex 线程能力、知识库能力和真实项目实践继续演进。
